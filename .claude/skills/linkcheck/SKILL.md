# Linkcheck

ウィキの外部リンクを検査し、意図した資料に届かなくなったものを直す。

出典のURLは、そのページの理解がどこから来たかを示す根拠になる。404 を返すリンクだけでなく、200 を返しても別のページに着地するリンク（転送先が文書のトップ、アンカーが別の節）も根拠を失っている。直すのはリンク先だけで、書かれた理解には触れない。

## 境界

- 直すのはURL・画像URL・アンカーだけ。本文の説明、題名、タグは変えない。リンク文字列は、指している節の見出しが改名されたときだけ合わせる。
- 製品の改名などで本文が古くなったと気づいても書き換えず、報告に残す。本文の事実の誤りに気づいた場合も同じ。本文はユーザーの理解の記録なので、書き換えるかはユーザーが決める。
- 置き換え先は、実際に開いて同じ資料だと確かめたものだけにする。URLを推測で組み立てない。
- ボット確認やCAPTCHAを越えようとしない。開けないものは未確認として報告する。
- 調査はサブエージェントに分担させず、このセッションで進める。
- ウィキの読み取りは scraps コマンドを使う。全ページを横断する機械的な検査は `mise run check-links` に任せる。

## 1. 検査する

1. `mise run check-links > <作業用ディレクトリ>/links.json` を実行する。全ページで数分かかるので裏で走らせてよい。特定のページだけなら `mise run check-links -- "scraps/<ページ>.md"` のように渡す。
2. 内部リンクは別に `mise exec -- scraps lint -r broken-link -r broken-heading-ref` で見る。
3. 結果の `status` を次の表で判定する。直し方を決める前に、誤検出を外す。

| `status` | よくある原因 | 確かめ方 |
|---|---|---|
| `dead` | 移転・削除。ページをブラウザ側で描画するサイトは、正常なページでも 404 を返すことがある | 内蔵ブラウザで開き、正しいページが出るなら誤検出 |
| `dns` | ドメインの失効、または最初から存在しないドメイン | 第2節の4 |
| `unreachable` | 一時的な障害や配信元の停止 | 時間を置いて再実行し、続くなら `dead` と同じに扱う |
| `blocked` | ボット対策でスクリプトからの取得を拒んでいる | 内蔵ブラウザで開いて題名を見る。確認画面が出たら未確認として残す |
| `redirected` | 移転や改名に伴う転送 | 第3節 |

アンカー付きのリンクには `anchor` が付く。`missing` の原因は、見出しの改名、別ページへの移動、JavaScript による振り分けのどれか。JavaScript による振り分けかどうかは、内蔵ブラウザで開けば分かる。`found` でも、`anchor_heading` とリンク文字列（`where[].text`）が別の話題なら、同じページの別の節を指している。

## 2. 移転先を探す

`dead` と `dns` は、次の順に移転先を探す。

1. **同じ資料が別の場所へ移った。** サイトの `sitemap.xml`・`llms.txt`・文書の目次から辿る。文書の元リポジトリの履歴（`gh api "repos/<owner>/<repo>/commits?path=<ファイル>"` で改名が分かる）や、リポジトリの `homepage` 欄も手がかりになる。
2. **製品や機能が改名された。** 変更履歴や、新しい文書にある「Renamed from ...」の記述で確かめ、新しいページを指す。本文やページ題名が旧名のままなら報告に残す。
3. **資料そのものが消えた。** Wayback Machine の最後の正常な保存を使う。
   - 可用性API（`archive.org/wayback/available`）はすぐ 429 になるので、CDX API で保存日時を引く: `https://web.archive.org/cdx/search/cdx?url=<URL>&output=json&fl=timestamp,statuscode,original&limit=-4`
   - `https://web.archive.org/web/<日時>id_/<URL>` を `curl --compressed` で取り、題名を確かめる。
   - リンクには `https://web.archive.org/web/<日時>/<URL>` を使う。
   - 転送（3xx）として保存された記録は、その転送先も見る。
4. **最初から存在しなかった。** 次の3つがそろうURLは、ページ作成時に作られた架空のURLとみなし、行ごと消す。そのページに残る出典を報告に書く。
   - DNS レコードが無い
   - Wayback の保存が 0 件
   - 公式の資料にも出てこない
5. **SNS のアカウントが消えた。** 同じサービスで確実に存在するアカウント（X なら `x.com/github`）を対照に開く。対照が開けて対象だけが 404 なら、消えたと判断して行を消す。ページの外部リンクがそれだけになる場合は、ページが既に使っている本人のサイト（画像の置き場など）があれば、Home として置き換える。
6. **人物の画像が消えた。** X のアイコンURLは、アイコンを変えるたびに変わる。GitHub の表示名とプロフィールのリンクで本人と確かめられたら、`https://avatars.githubusercontent.com/u/<ID>?s=200&v=4` に置き換える。確かめられなければ推測で埋めず、壊れた画像の行を消す。

どの置き換え先も、次の2点を確かめてから使う。

- 200 で開ける
- 題名・見出し・本文の一部が、元の資料（リンク文字列や Wayback の保存）と一致する

## 3. 転送を扱う

`redirected` は今は開けるので、次のどれかに当てはまるものだけを転送先へ書き換える。

- 転送元のドメインが廃止され、パスを機械的に写すだけの転送になっている。新しいサイト側でページが改名されると、旧URLからは 404 になる（例: `docs.anthropic.com` から `code.claude.com`）。
- 転送先が、個別のページではなく文書のトップなどの汎用ページになっている。開けても実質はリンク切れなので、第2節で個別のページを探す。
- ドメイン変更やリポジトリ移管で、移転元がもう使われていない。

次のものは書き換えない。

- 広く使われていて安定した転送（`twitter.com` から `x.com`）
- 言語の指定や末尾スラッシュだけの違い
- `stable` のような版の別名
- 後継が1つに決まらないもの

版ごとに分かれた文書は、日付や番号の入ったパスより、最新版へ転送される版なしの別名を選ぶ。

## 4. 直してPRにする

- 1つのPRは1つの理由にまとめ、編集は10件前後までにする。理由の例は次のとおり。ユーザーは小さなPRを次々に受け取る方を好む。
  - 文書の移転
  - 消えた資料を Wayback へ
  - 存在しなかったURLの削除
  - 製品の改名への追従
  - アンカー違い
  - 転送元の廃止
- ブランチは最新の `origin/main` から切る。まだマージされていない別のPRと同じ行か隣の行を触る編集は、git が衝突として扱う。そのPRがマージされてから出す。
- 置き換える前に、元の文字列がそのファイルにちょうど1回現れることを確かめる。
- コミットメッセージは英語で書く。PR本文は日本語で書き、次の2つを載せる。
  - 「ページ・旧→新・根拠」の表
  - 調べたが直さなかったもの
- 出す前に `mise exec -- scraps lint -r broken-link` と、変更したページだけを対象にした `mise run check-links -- <ファイル>` で確かめる。

## 5. 報告する

次の5つを分けて報告する。

- 出したPR
- 誤検出だったもの
- 未確認のもの（ボット確認で開けないサイト）
- 書き換えなかった転送
- 本文が古くなったと気づいたページ
